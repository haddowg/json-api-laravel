# The served OpenAPI document is decorated per request from serialized value objects

Build-time decorators can't see the request, so one deployment serving many hosts couldn't give each host its own `servers`, hide a tenant's disabled operations or rewrite example hosts. `OpenApiServeDecoratorInterface` and `JsonSchemaServeDecoratorInterface` run in the docs controllers with the `Request`, after `artisan optimize` has done the expensive build. They are bound and tagged like the build-time `OpenApiFactoryInterface` and run in registration order. The CLI exporters and the static `public_path` files stay undecorated, because the committed spec is the full contract for diffing and codegen.

## Considered options

Core's OpenAPI value objects have no `fromArray()`, so a decorated request needs a way back from the warmed artifact to value objects. A hydrator in core would be a second, hand-maintained copy of every value object's serialisation, run on every request. Instead the warmer PHP-serializes the document beside its JSON (`<server>.serve`) through core's `ServeArtifactCodec` and a decorated request decodes it. With no serve decorator tagged the controller never touches that file and serves the warmed JSON bytes as before. The pruning, the codec and the ETag recipe are core's `OpenApi\Serve` helpers (core ADR 0159), shared with the Symfony bundle; the decorator interfaces, controllers and cache location stay here.

Decorators only remove things and the package prunes what they orphaned, so app code never walks `$ref`s. Only components reachable from the warmed document's paths are candidates; components it never referenced, or that a decorator added, are kept and act as roots, so a kept component can't end up with a dangling reference. Path items with no operation and tag definitions whose operations all went are dropped. Relationship members whose related type lost its endpoints are left alone, because the parent's responses still carry that linkage. Security schemes are referenced by name and left alone too.

The ETag has three modes. With no serve decorator it is the artifact's hash, written beside the artifact, so a 304 costs one small read. When every decorator of a kind implements `OpenApiServeCacheKeyInterface`, the ETag hashes the artifact hash with each decorator's class and key in run order, and `If-None-Match` is checked before anything is loaded or decorated. If any decorator lacks a key the ETag falls back to the hash of the final body, because a partial key would let two different bodies share a tag. Comparison is weak so a CDN's `W/` tag still matches.

`jsonapi.openapi.cache_control` is off by default, because docs routes are often behind authentication and a `public` default would let a shared cache hand one user's document to another. No `Vary` is sent: the routes always return JSON and a CDN already keys on the host. The docs routes are registered outside any middleware group, so the `web` group's session and cookie middleware never reach them.

## Consequences

A cache key doesn't change when a decorator's logic does, so keys should carry a version the author bumps. The artifact directory under `storage/` survives a deploy, unlike a framework cache that is rebuilt each time, so a `composer update` without `optimize` would leave value objects serialized against old classes. The codec writes the installed core and package versions into each artifact's header and reads it as missing once they change, and the document is rebuilt instead. It unserializes only core's value objects, `stdClass`, enums and the classes in `jsonapi.openapi.serve_allowed_classes`, so a document holding any other object gets no artifact: the warmer logs a warning for that server and decorated requests build it.
