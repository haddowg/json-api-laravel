# A polymorphic to-many is narrowed per member type

ADR 0032 refused, with a server error, to render a polymorphic to-many that reaches a type served by its own scoping provider, because no single provider could load its members. Such a relation is now read like any other: its members are loaded off the parent as the candidates, grouped by member type, and each member type with its own scoping provider narrows its candidates in one lookup across every parent at that level, through `FetchesManyInterface::fetchMany()` when the provider implements it and `fetchOne()` per id otherwise. Members of other types are kept as loaded, since a reference provider's rows are exactly what the relation read yields. The narrowing runs before any page is cut or count taken, so linkage, `included`, both endpoints and `?withCount` show the same members and every count matches them, and the narrowed linkage reaches core through the out-of-band linkage seam that monomorphic to-manys already use, never by writing onto the parent. We chose a batched id lookup over refusing because one provider per member type can each answer for its own rows, which is all a mixed relation needs.

## Consequences

Writes need no new rule: a relationship write already resolves each named id through its own member type's provider (ADR 0034), so a hidden id is a `404` and a replace keeps the hidden current members. A related page of mixed types also preloads each member type's own includes, so a member's relation into a scoped type is scoped too. A computed closure's members follow ADR 0050: Eloquent global scopes apply to the queries the closure runs, and a closure that removes them is not probed. This needs core 1.10, whose `MorphToMany` reads the linkage seam. The Symfony bundle applies the same rule.
