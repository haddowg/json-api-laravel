# A server may declare its own response-header defaults

The `jsonapi.defaults` cache, deprecation and sunset headers applied to every server, so an app running two API versions side by side could deprecate the old one only by declaring the same `deprecation` and `sunset` on every resource class it serves. Each server now takes the same `defaults` block under `jsonapi.servers.<name>`, matching bundle ADR 0164, and the `ResponseHeadersRegistry` resolves each value from the resource's own declaration, then its server's block, then the global one. The layers merge key by key with the existing `mergeOver`, so a server that sets only a sunset keeps the global deprecation, and cache directives keep their merge: unset values inherit, `no_cache` and `must_revalidate` switch on at any layer, and `vary` lists add up. We kept the global block as the fallback for every server, rather than making a server's block replace it whole, because the reason to add one is to change a header or two for a single version. The OpenAPI projection describes none of these headers or a deprecated flag, in this package or the bundle, so byte-compat is unchanged.

## Consequences

The global block had no checks, so a bad value emitted no header without saying why. `ResponseHeaderDefaultsConfig` now checks the global block and every server's while the app boots, against the keys and types the bundle's config tree accepts, and throws on the first bad one. That includes an `operations` map under the global `cache_headers`, which the registry never read; per-read-shape overrides stay on the resource attribute.
