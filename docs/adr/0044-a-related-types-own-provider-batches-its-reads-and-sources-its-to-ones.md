# A related type's own provider batches its reads and is the source of its to-ones

A relation whose related type has its own provider used to load through that provider once per parent, so includes, linkage, counts and windows cost one call per parent at every level. Those reads now ask the related provider's existing `fetchRelatedCollectionBatch()` for the whole page first, with parents of another type keyed by their wire id, and read only the parents it leaves out one at a time, so the base class's empty batch keeps today's behaviour without a new SPI method. For a to-one the answered batch is the target itself, on every read path including the related and relationship endpoints and a `relatedQuery` filter, rather than a check on a target read off the parent: a read-only type a provider computes per page, such as a progress summary, can then hang off a model with no relation method, and the deploy-time relation method check skips such a relation.
