# A relation declared with a foreign key is read and written by its related type's provider and persister

A to-many on a parent no Eloquent model serves, such as a singleton a custom provider serves, had nothing to read its members from: the Eloquent provider scopes a related query by the parent model's relation method, and the parent has none. A relation declared with a foreign key is now always read by the related type's provider through `ReadsByForeignKeyInterface`, handed the page of parents keyed by wire id with the keys their rows hold, so it pushes down one `WHERE <foreign key> IN (...)` query under the related model's global scopes and windows it per parent with `ROW_NUMBER()`, whatever provider serves the parents and even when the parent model has a relation method for it. Its relationship writes go to the related type's persister through `WritesForeignKeysInterface`, which sets the key on the rows joining the parent and clears it on the rows leaving, since the parent's persister has no column to write; the handler works out both sets from the linkage and the members the reads serve, so the scope, the move gate, the hooks and the transaction behave as for any relationship write. A to-many with no foreign key on such a parent reads what the parent model holds, cut in memory, and `jsonapi:optimize` refuses it only into a model with global scopes, which that read can't apply; route registration checks only the declared foreign keys, so a boot builds no provider for a resource that declares none.
