# Pivot meta rides the include through a rendering resolver

A pivot relation's `meta.pivot` belongs to a parent and a member, and a relation reached through `?include` is built by a resource whose resolver is the server, which knows neither. A document therefore resolves its serializers through `PivotRenderingResolver`, which decorates every type that reaches a pivot relation so its relationships are built back through the same resolver at every depth, and binds each parent's pivot relation to a `PivotMetaSerializer` that reads the stored values off the pivot row the include's query already hydrated on the member. Reading them off the member, rather than batching a separate pivot map per level as the bundle does for the primary type, keeps the include walk the only place that queries and gives every depth the same path. When a member comes back without its pivot row, as from a provider that doesn't query the join, the stored values come from one `PivotAwareProviderInterface::fetchRelatedPivotMapBatch()` per pivot relation, the method the bundle's providers implement, over every parent of that type the include walk loaded, never a read per parent.
